All three fields arrive masked

Mollie's API keys used to render as plain text inputs on the module Settings tab, readable by anyone looking at the screen. Both are now masked behind a reveal toggle, and so is the website profile id — for a weaker reason, kept distinct throughout. This page is the browser evidence, and an honest account of what it does and does not protect.

What was actually changed

One constant, one template override, four lang lines. No service, no interface, no controller extension, no migration.

The template does not name the keys. It reads the list from the constant, so adding a future credential setting masks it with no template edit — there is no second list to drift out of step with the first: 

{% set mollie_secret_settings = constant(
    'OxidEsales\\Payments\\Mollie\\Core\\MollieDefinitions::SECRET_MODULE_SETTINGS'
) %}
{% if mollie_is_mollie_module and module_var in mollie_secret_settings %}
    <input type="password" … data-mollie-secret autocomplete="off">
    <button type="button" class="mollie-key-toggle" aria-pressed="false">…</button>
{% else %}
    {{ parent() }}
{% endif %}

Why this needed a browser to verify

constant() is core Twig, but nothing in the PHP suite can tell you whether OXID's Twig environment permits it. Had it been restricted, the {% if %} would simply yield false, every key would fall through to {{ parent() }}, and the tab would render exactly as it did before — keys in clear text, and no error anywhere. A silent failure in the revealing direction. That is why nothing was committed until the screenshots below existed.

Story 4 — the four-deep chain

Four active modules override the same admin template, on top of the stock one. That makes {{ parent() }} delegation load-bearing rather than tidy: an override that swallows the block blanks out the settings form of every module earlier in the chain. What this does not protect against

The key still reaches the browser

The value is rendered into the value="" attribute. Masking stops shoulder-surfing, screen sharing and screenshots. It does not hide the key from anyone who opens devtools or view-source — and anyone with access to this form can read the key by saving it anyway.

Do not describe this as making the credential confidential. A true never-send-the-secret implementation needs save-side PHP, and was explicitly deferred.

And the profile id is not a secret at all

The pfl_… website profile id is masked alongside the keys, but for a weaker reason that the code, the tests and the sprint notes all keep separate: it is shipped to the browser by the storefront checkout widget for new Mollie(profileId, …). Masking it in admin protects nothing against anyone who can read the shop's own frontend.

What it buys is screen hygiene — an account identifier that no longer sits in plain view during a screen share, and one fewer field an operator has to reason about. A test asserts the constant keeps documenting that distinction, so nobody later concludes from the list that the profile id is confidential, or strips the masking on the grounds that it isn't.

Revised after review

The first pass left the website profile id visible, on the argument that masking a value the storefront already publishes implies a confidentiality it does not have. That argument is sound and is still recorded in the sprint notes — but it was overruled on operator preference: keeping an account identifier off the screen during a screen share costs nothing, and a tab where every string field behaves the same way is one less thing to reason about.

Two things followed from masking a third, non-credential field. The toggle's aria-label could no longer say “Reveal API key” — on one of the three that is simply wrong — so the idents are now MOLLIE_REVEAL_VALUE / MOLLIE_HIDE_VALUE. And the drift guard's name heuristic became a subset check rather than an equality, because the masked list now deliberately holds something the heuristic would never flag.

Found while proving it

OXID already has a password setting type — and it is better than this

The stock template supports 'type' => 'password' for module settings (module_config.html.twig:81-84), rendering <input class="password_input" type="password" name="confpassword[…]"> with no value attribute at all. The secret is never sent to the browser — which is exactly the "never-send-the-secret" work this sprint deferred as needing its own sprint.

So the shipped approach is second-best, and the honest recommendation is to switch the two settings to the native type and delete the override entirely. It is not a free swap, which is why it was not done here: the value moves from the confstrs POST bucket to confpassword, and because the field renders empty, submitting the form without retyping the key appears to save an empty string over a live credential. Both need verifying on a throwaway shop before any change — getting it wrong wipes a merchant's API key and breaks checkout.

Log-level translations — found here, fixed after

Earlier versions of these screenshots showed the Log level select reading ERROR: Translation not found: the four SHOP_MODULE_sMollieLogLevel_* option idents had never been added, so OXID rendered its missing-ident text inside every <option>. It was left alone at first — a translation fix inside a security diff muddies the review — then done as its own change, which is why the select reads properly above.

The interesting part is not the four strings. It is that nothing failed: a `select` setting with no option idents ships the error text to production and no test notices. So the fix came with SelectSettingTranslationsTest, which derives the expectation from metadata.php — every select setting must have a label and an ident per constraint value, in both shipped languages, and en/de must cover the same set. A new setting or a new option value is covered the moment it is declared.

It caught a repeat the same day. An unrelated commit (opc-125 rev-56) landed a new select setting, sPaymentHandlerUiTopology, plus a new MOLLIE_ADVANCED group — with no translations for either, in either language. The guard flagged the select immediately; it did not flag the group header, so that check was added too. Both are translated now. They do not appear in the screenshots above because module configuration is only refreshed from metadata.php on install/activate, and this shop has not been re-activated since that setting was declared — so the tab still renders the seven settings it knows about.

The drift guard is the one that matters over time. A setting whose name ends in key, secret, token or password must appear in the masked list, and every listed name must be a real setting in metadata.php — so a future credential cannot ship unmasked, and a typo in the list cannot mask nothing. Note it is a subset check, not equality: the list is deliberately allowed to hold fields the name heuristic would never flag, which is what makes room for the profile id.

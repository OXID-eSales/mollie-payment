The API keys are masked

Mollie's two API keys used to render as plain text inputs on the module Settings tab, readable by anyone looking at the screen. This page is the browser evidence that they no longer do — and an honest account of what that does and does not protect.

What was actually changed

One constant, one template override, four lang lines. No service, no interface, no controller extension, no migration.

The template does not name the keys. It reads the list from the constant, so adding a future credential setting masks it with no template edit — there is no second list to drift out of step with the first: 

{% set mollie_secret_settings = constant(
    'OxidEsales\\Payments\\Mollie\\Core\\MollieDefinitions::SECRET_MODULE_SETTINGS'
) %}
{% if mollie_is_mollie_module and module_var in mollie_secret_settings %}
    <input type="password" … data-mollie-secret autocomplete="off">
    <button type="button" class="mollie-key-toggle" aria-pressed="false">…</button>
{% else %}
    {{ parent() }}
{% endif %}

Why this needed a browser to verify

constant() is core Twig, but nothing in the PHP suite can tell you whether OXID's Twig environment permits it. Had it been restricted, the {% if %} would simply yield false, every key would fall through to {{ parent() }}, and the tab would render exactly as it did before — keys in clear text, and no error anywhere. A silent failure in the revealing direction. That is why nothing was committed until the screenshots below existed.

Story 4 — the four-deep chain

Four active modules override the same admin template, on top of the stock one. That makes {{ parent() }} delegation load-bearing rather than tidy: an override that swallows the block blanks out the settings form of every module earlier in the chain. What this does not protect against

The key still reaches the browser

The value is rendered into the value="" attribute. Masking stops shoulder-surfing, screen sharing and screenshots. It does not hide the key from anyone who opens devtools or view-source — and anyone with access to this form can read the key by saving it anyway.

Do not describe this as making the credential confidential. A true never-send-the-secret implementation needs save-side PHP, and was explicitly deferred.

Found while proving it

OXID already has a password setting type — and it is better than this

The stock template supports 'type' => 'password' for module settings (module_config.html.twig:81-84), rendering <input class="password_input" type="password" name="confpassword[…]"> with no value attribute at all. The secret is never sent to the browser — which is exactly the "never-send-the-secret" work this sprint deferred as needing its own sprint.

So the shipped approach is second-best, and the honest recommendation is to switch the two settings to the native type and delete the override entirely. It is not a free swap, which is why it was not done here: the value moves from the confstrs POST bucket to confpassword, and because the field renders empty, submitting the form without retyping the key appears to save an empty string over a live credential. Both need verifying on a throwaway shop before any change — getting it wrong wipes a merchant's API key and breaks checkout.

Missing log-level translations, visible in every screenshot

The Log level select reads ERROR: Translation not found: the SHOP_MODULE_sMollieLogLevel_* option idents were never added. Real, pre-existing, and deliberately not fixed here — a translation fix inside a security diff muddies the review. Its own one-line change.

The drift guard is the one that matters over time. It reconciles the secret list against metadata.php in both directions, so a future credential setting cannot ship unmasked and a typo in the list cannot mask nothing. It also fails if a setting whose name ends in key, secret, token or password is left off the list.
